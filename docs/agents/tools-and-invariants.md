# Tools, invariants, AI visibility and AiId

Read this when you add a tool, an invariant, a describer, or touch `AiId` or `AiVisible`. Part of the [AGENTS.md](../../AGENTS.md) index.

- Write what must always hold in the game as an invariant:
  `add_ai_invariant(name, |w: &World| -> Option<String>)`. The rule only reads the world and returns
  the text of the violation with the entity's id (`e6 Health.current = 700 outside 0..=600`). Rules and their firings
  are not part of the replay hash or the snapshot; the replay records session rules (`assert_add`) as events.
  The engine's own rules are named `<module>.<rule>` and registered with `add_engine_invariant(name, rule)` (shards_core): on by
  default, off in a `dist` build and with `--no-engine-invariants` (`EngineConfig::engine_invariants`; tests, `--verify`, fuzz and soak
  keep them on). A rule not yet proven on all content is offered with `add_opt_in_engine_invariant`
  and checked only when named: `--engine-invariant NAME` (`EngineConfig::opt_in_invariants`); none is today (`voxel.body_in_solid`
  was, until its fuzz runs). Each states in its doc comment what it checks and why any carve-out exists, and has a control test that breaks the
  state on purpose. If one fires, it is a bug in the engine or the game: fix the bug, do not weaken the rule without saying why.
- A new tool is an argument struct with doc comments (they become the schema's description)
  and a Bevy system `In<Call<Args>> -> ToolResult`. Kinds: `query` reads, `action` changes the world
  (journal, diff, replay), `control` manages time and the session. A tool error says how to fix the call.
- The AI sees only entities with `AiVisible` (`AiKind` gives it). What is said about them is decided by
  the describe functions (`register_ai_component`, `register_ai_describer`, and `register_ai_world_describer` for a fragment that needs the world around the entity: `finishable by e5`).
- The engine assigns `AiId`. Do not write it in place (`get_mut`, `set`, BRP `world.mutate_components`):
  the "id → entity" index is kept by the `on_insert` and `on_discard` hooks. Inserting a new `AiId` renumbers
  the entity, and the old id gets a tombstone `renumbered to eN`.
- Encounters (`shards_encounter`): the tools are `encounters`, `encounter key=K`, `encounter_start key=K [wave=N]`, `encounter_clear key=K` and `encounter_reset key=K|all
  [forget=true]`; the conditions `encounter_active`, `encounter_between`, `encounter_wiped`, `encounter_won` and the NPC condition
  `encounter_returning`; the engine rules `encounter.members_tracked`, `encounter.state_sane` and `encounter.lock_matches`. A prefab a run counts
  needs an `AiId` (`AiKind`). A game plugs a downed state in with `add_encounter_out_rule` and cleans up what a member owns with
  `add_encounter_despawn_hook`.

- Combat objects (B4) add the engine rules `action.objects_sane` (an object has an owner in the world; a projectile holds finite numbers and a unit direction) and `action.objects_capped` (no more than `max_objects` alive in a tick that spawned some), the query `combat_objects`, the conditions `objects_live` and `projectile_flying`, and the describers `object` and `projectile`. A combat object carries `NoTombstone` (required by `CombatObject`): it leaves no tombstone in the `AiIndex`, so a radial cast cannot push the ids worth remembering out of the graveyard. Spawn objects only through `spawn_objects`, which keeps the caps; a prefab with a `CombatObject` made by hand trips `objects_capped`.
- Weapons (F4) add the engine rule `action.arsenal_sane` (an `Arsenal`'s slots ascend in 1 to 9, `current` and `pending` name one of them, no charge of the body is above its maximum), the tools `reload`, `weapon` (player) and `give_weapon`, `take_weapon`, `give_ammo` (dev), and the describer `weapon`. The arsenal is state on an `AiId` body (reflected: snapshots and the replay hash see it); a switch asked for waits in `Arsenal::pending`, never in a resource. Write a pickup with `grant_weapon` and `add_to_charge`, never by writing the component: they keep the body's moveset, `bare` and charges in step.
- Movers (F6) add the engine rule `motion.mover_sane` (a `MoverState`'s `t` in `0..1`, 0 at rest, neighbouring keys, finite times and origin, no key past its definition's last), the dev tools `mover_go` and `level_despawn`, the condition `mover_arrived` and the describer of a `Mover`; a mover's parts carry an `AiId` but no `AiVisible` (plumbing).
- Shooting (F3) adds the player tool `fire`, the player query `shot_trace` and the `SHOT` observe line, and no engine rule. A shot resolves inside `ActionSystems::Effects` and keeps nothing between ticks but the bodies it changed: the per-tick shot ordinals that key the pellets' draws (`shot::Shooting`) are emptied in `FixedLast` and listed outside snapshots in `state_audit.rs`. Its pellets' `Damaged`/`Blocked`/`Parried`/`Evaded`/`GuardBroken` journal lines are folded into the shot's one line (`shot::resolving`); a new journal formatter for a per-hit event does the same. Aim from `shot_ray` (pure, no draws), never from a camera.
- NPC gunfire (F11) adds the dev tool `turret_active`, the conditions `npc_hidden` and `npc_line_blocked`, the describer `npc_ranged` (hiding, range, line of fire, turret) and the journal line `e9 turret on|off` (`TurretSwitched`), and no engine rule: the existing `npc.*` rules hold over ranged NPCs and turrets. `npc_state` and `npc_schedule` read the hiding spot and the line of fire from the NPC's components and never search or trace themselves, so a tool call changes nothing; a new tool about F11 state does the same and reads content with `db.peek`.
- Crouching (F2) adds the player tool `crouch` (and the `stance=` argument of the queries `clearance` and `path_to`), the events `Crouched` and `Stood` (journalled) and the component `Crouch { depth, wanted, blocked }`, no engine rule (`motion.finite` also judges `Crouch::depth`). The stance is a reflected component beside `MotionState`, put on a body by the controller the first time it crouches and never on one that cannot: a new field of `MotionState` or `LocomotionInput` would change the replay hash of every body, so state that only some bodies have goes in a sibling component. The input is `Intent::held` `crouch`, read in the controller. Whatever needs the size of a body asks `CharacterParams::at_depth(depth)` (and `eye_of` for the eye), never `CharacterParams::height` directly.
- Scenes (F12) add the dev tools `lock_controls`, `unlock_controls`, `sequence_play` and `sequence_stop`, the query `sequences`, the condition `sequence_playing`, the `CONTROL` line and the `SEQUENCE` lines of `observe`, the describer `sequence` (an NPC's `in sequence 1 scene_intro (guide), step 3/6`), `npc_state.sequence`, and the engine rules `motion.control_lock_sane` (a `ControlLocks` that `lock_controls` could not have made) and `npc.sequence_holds` (a hold names a run that plays, a run's actor in the world carries the hold, numbers ascend below `next`, no step past the end). A body in `sequence_play` is an id or a name only one body has (`role.guide=Guide`), so a scenario names no spawned id. The player's movement and combat tools have guards that refuse with the lock's reason; a new player tool that moves or acts adds a guard in `control_lock/tools.rs`, or it works through `Intent` and the lock still stops it, only silently.
