# ТЗ: что добавить в движок Shards, чтобы сделать «Осколки Предела»

13 Oct 2026 · @Larel

Движок Shards (репозиторий airustcargo) должен стать набором крейтов, на котором отдельный репозиторий игры
собирает «Осколки Предела», не трогая код движка. Ниже 11 модулей E1–E11: что в каждом сделать, где граница
с игрой, что видит ИИ и когда модуль готов. Номера разделов GDD указаны по документу игры.

Ход работ по этому ТЗ — в [engine-progress.md](engine-progress.md).

## Граница движка и игры

- Движок даёт механизмы и инструменты: физику, систему действий, сеть, сохранения, генератор по правилам,
  виджеты интерфейса, слой ИИ.
- Игра даёт содержание и числа: оружие, атаки, врагов, боссов, тайлы, регионы, сюжет, баланс, внешний вид.
- Проверка: если механизм пригодится второй игре с другим сюжетом — он в движке. Если это конкретное «что» — в игре.
- В движке нет кода с именами из GDD (Корнерог, Ветролесье, Эхо и т. п.).
- Песочница остаётся тестовой ареной движка: на ней проверяется каждый модуль.

## Общие требования ко всем модулям

1. AGENTS.md: в движке нет LLM; код и комментарии на английском, документация на русском; Bevy 0.20.0.
2. Симуляция — в `FixedUpdate` внутри `SimSet`, случайность — только `SimRng`. Компоненты нового модуля входят
   в хэш реплея и записываются в реплей.
3. Всё, что влияет на геймплей, работает без окна и рендера одинаково с окном.
4. Каждый модуль открыт ИИ: состояние — через describe-функции, события — через `journal_event`, действия — через
   `add_ai_tool` и `add_ai_query`, стоп-условия — через `add_ai_condition`.
5. Числа и определения лежат в файлах ассетов с горячей перезагрузкой. Подстройка баланса не требует пересборки.
6. Сторонний крейт выбирается только после проверки: поддерживает ли Bevy 0.20 и жив ли проект. Версия
   закрепляется, а сам крейт прячется за API движка — игра не импортирует его напрямую. Тогда крейт можно
   заменить, а Bevy — обновить без правок игры.
7. У каждого модуля: юнит-тесты, сценарий в песочнице, проверка реплеем, раздел README.
8. Модуль — серия PR. Начинать с фазы A (схема фаз ниже).

## Архитектура

```text
            игра «Осколки Предела» (отдельный репозиторий)
                               │ зависит только от
                               ▼
                     shards (зонтик: EnginePlugins, EngineConfig, prelude)
                               │
   ┌──────────┬──────────┬─────┴─────┬──────────┬──────────┬──────────┬──────────┐
 core      motion     action     content     world       npc        net       save · ui · platform
   └──────────┴──────────┴─────┬─────┴──────────┴──────────┴──────────┴──────────┘
                               │ подключён ко всем модулям
                            ai_core  ──►  shards CLI  ◄── агенты · CI · человек
                               │
               сторонние крейты (физика, сеть, …) — только внутри модулей
```

Игра видит только крейт `shards`. Модули и сторонние крейты внутри движка можно менять, не трогая игру,
а `ai_core` подключён ко всем модулям и доступен агентам, CI и человеку через `shards` CLI.

Предлагаемые крейты: `shards` (зонтик), `shards_core`, `shards_motion`, `shards_action`, `shards_content`,
`shards_world`, `shards_npc`, `shards_net`, `shards_save`, `shards_ui`, `shards_platform` плюс существующие
`ai_core`, `sandbox` и `shards_cli`. Мелкие модули можно объединять; неизменна только граница «игра зависит
от `shards`».

## E1. Ядро, сборка и шаблон игры

Игра живёт в отдельном репозитории и подключает движок одной зависимостью. Режим без окна — тот же движок,
только без картинки: по GDD (32.8) генератор и тесты гоняются без окна на тысячах зёрен.

Что сделать:

1. Крейт `shards` — единственная зависимость игры: группа плагинов `EnginePlugins` и настройка `EngineConfig`
   (окно или без окна, порт для `shards`, seed, частота тика, включённые модули). Крейт реэкспортирует нужное
   из Bevy и модулей.
2. Режим без окна собирается из тех же плагинов, что и с окном, минус окно, рендер и звук. Работают трансформы,
   ассеты, сцены, состояния и физика. Сейчас песочница без окна собрана из `MinimalPlugins` — это заменить.
3. Состояния приложения: загрузка, главное меню, игра, экран загрузки региона, пауза. Общий механизм на Bevy
   States с точками расширения для игры.
4. Версии движка: семантические версии, теги git, CHANGELOG. Игра подключает движок по тегу.
5. Шаблон игры в `template/`: минимальная игра только на `shards` — персонаж, враг, арена, сохранение, кооп на
   двоих. Шаблон растёт вместе с модулями.
6. CI движка на GitHub Actions: тесты, clippy, сборка шаблона, `--verify` эталонных реплеев из `tests/replays/`
   (папка `replays/` в .gitignore).

Граница: игра добавляет свои плагины поверх `EnginePlugins` и не меняет код движка.

Для ИИ: `ai/status` показывает версию движка и включённые модули.

Готово, когда:

- шаблон собирается и проходит тесты отдельно от песочницы;
- один и тот же реплей совпадает с окном (под Xvfb) и без окна;
- CI зелёный на каждый PR.

## E2. Движение: физика, персонаж, ввод, камера

Движку нужна физика и контроллер персонажа под список из GDD 11: ходьба, бег, прыжок, перелезание, плавание,
уклонение, планер. Плюс ввод и камера из GDD 13.2 и 29.2: захват цели, геймпад, переназначение, удержание или
нажатие, тряска, поле зрения.

Что сделать:

1. Физика (кандидат — avian3d) в `FixedUpdate`, детерминированная на одной машине и сборке. Слои коллизий,
   триггер-объёмы, API raycast и shapecast для геймплея и ИИ.
2. Кинематический контроллер персонажа: ходьба, бег, спринт, прыжок, шаг через ступеньки, перелезание низких
   препятствий, склоны с предельным углом, плавание по поверхности, планер (медленное падение и объёмы
   восходящих потоков). Падение с высоты — событие для игры.
3. Параметры контроллера — ассет с горячей перезагрузкой.
4. Ввод: карта действий (кандидат — bevy_enhanced_input) превращается в `Intent`. Клавиатура, мышь, геймпад;
   переназначение с сохранением; удержание или нажатие; контексты (игра, меню, прицеливание). Единственный путь
   управления персонажем — `Intent`, как сейчас.
5. Камера от третьего лица: орбита, столкновение со стенами, захват цели и переключение целей, настраиваемая
   помощь при прицеливании, отключаемая тряска, поле зрения. Камера — только представление: геймплей и
   восприятие ИИ от неё не зависят.
6. Предупреждение об атаках за кадром (GDD 13.7): API, который по зонам атак из E3 даёт направление для
   индикатора.

Граница: скорости, высота прыжка, параметры планера и потоков — данные игры.

Для ИИ: режим движения (земля, воздух, вода, планер) и скорость в describe; инструменты `jump`, `sprint`,
`glide`; запросы `clearance` и `path_to` из E11 работают по физике.

Готово, когда: агент скриптом проходит в песочнице полосу препятствий — ступеньки, уступ, вода, обрыв с
планером. Без окна и с окном результат одинаковый, реплей полосы совпадает.

## E3. Действия, бой и анимация

Атаки в GDD (13.4) — это данные: подготовка, активное окно, восстановление, окна отмены, движение, урон, урон
стойкости, форма хитбокса, переходы, сетевой id. Та же система работает у врагов и боссов. Плюс выносливость,
окно неуязвимости около 0,18 с и буфер ввода около 0,15 с (13.3), стойкость (13.5), статусы (15), общие
скелеты (30.2).

Что сделать:

1. Действие — ассет: фазы с длительностями; окна отмены и разрешённые переходы; кривая смещения (запечённая из
   анимации вместо root motion в рантайме); стоимость (выносливость, перезарядка); хитбоксы по активным кадрам
   (сфера, капсула, конус, коробка, линия по земле); флаги вроде «неблокируемая» или «пробивает защиту»; сетевой
   id. Это заменяет нынешний `Action` песочницы.
2. Машина действий персонажа: запуск из `Intent`, буфер ввода (из задачи 4), отмены по окнам, комбо как цепочки
   переходов, блок и идеальный блок как окна, уклонение с окном неуязвимости.
3. Хитбоксы и хёртбоксы проверяются в `FixedUpdate` через физику (shapecast), без опоры на кости и кадры
   рендера. Одно действие попадает по одной цели один раз.
4. Конвейер урона: попадание → модификаторы (блок, неуязвимость, броня, условия крита как хуки игры) → урон
   здоровью и стойкости → события `Damaged`, `Staggered`, `Died`. Попадания обрабатываются в порядке `AiId`,
   а не в порядке запроса.
5. Ресурсы бойца: здоровье; выносливость с задержкой восстановления; стойкость с восстановлением и состоянием
   пробития.
6. Каркас статусов без конкретных эффектов: накопление, порог, эффект при заполнении, длительность, лимит
   одновременных статусов, сопротивление как множитель.
7. Анимация: импорт glTF со скинами; граф анимаций, который следует за состоянием действия (геймплей ведёт,
   анимация догоняет); смешивание и переходы; общий скелет и переиспользование клипов. События анимации — только
   для эффектов и звука.
8. Телеграфы: зоны атак на земле и звуковые метки из данных действия. Опасность читается не только по цвету: у
   зон есть символы (GDD 13.7).

Граница: конкретное оружие, мувсеты, числа, горение, холод, импульс и боссы — данные и код игры.

Для ИИ:

- describe фазы действия с оставшимся временем и зоной удара;
- вывод для субъекта: «ты в зоне удара, выйди на N м»;
- инструменты `light_attack`, `heavy_attack`, `block`, `parry`, `use_technique`, `lock_on`;
- отказы действий журналируются, как в задаче 4.

Готово, когда: песочница на данных воспроизводит прототип боя из GDD 39 — комбо из трёх ударов, тяжёлая атака,
блок, уклонение, выносливость, враг с четырьмя атаками, стойкость, лечение. Агент проходит этот бой скриптом,
без окна и с окном одинаково, реплей совпадает.

## E4. Контент и уровни

GDD держит контент в данных (32.1 ContentDatabase, 32.3) и строит мир из заранее сделанных участков (10).
Редактора у Bevy нет, поэтому движку нужны база контента и конвейер уровней из Blender.

Что сделать:

1. База контента: типизированные определения (действия, оружие, враги, предметы, POI, события, тайлы) как
   ассеты RON или JSON, а когда в Bevy появится загрузчик `.bsn` — как BSN. У каждого определения стабильный
   строковый id. Горячая перезагрузка. При загрузке проверяются схема и ссылки, ошибки понятные.
2. Конвейер уровней из Blender: glTF с пользовательскими свойствами превращается в компоненты движка (кандидат —
   Skein). Маркеры: точки появления, сокеты тайлов, связи навигации, триггер-объёмы, интерактивные объекты,
   лагеря, ориентиры.
3. Префабы: сущность из ассета плюс переопределения полей (BSN-сцены, когда будет загрузчик `.bsn`).
4. Команда `shards content check`: все ассеты загружаются, ссылки целы, обязательные маркеры на месте.
5. Детерминированная загрузка: симуляция стартует, только когда загружены все нужные ассеты, и загрузка не
   сдвигает тики.

Граница: сами тайлы, POI, комнаты, предметы и их числа — ассеты игры.

Для ИИ: инструменты `content_list` и `content_get` (что есть в базе), `spawn_prefab`, перезагрузка ассета по
имени. Ошибки контента пишутся в журнал.

Готово, когда: шаблон собирает уровень из Blender-файла с маркерами; правка числа в ассете действия видна в
запущенной игре без перезапуска; `content check` находит битую ссылку и называет файл.

## E5. Генерация мира и стриминг

GDD собирает регион из сетки около 8×8 макротайлов по ~96 м с сокетами на краях, проверяет его и при неудаче
повторяет или берёт резервный вариант (10.1–10.2). Манифест и версия генератора хранятся навсегда (10.3),
подземелья собираются из комнат (10.4), регионы меняются через экран загрузки (7.1). Критерий этапа 4:
1000 зёрен без недоступных обязательных точек.

Что сделать:

1. Каркас генератора по шагам: зерно → граф обязательных точек → дороги → обязательные клетки → заполнение
   совместимыми тайлами с поворотами → второстепенные точки → оформление → проверки → повтор или резервный
   манифест. Шаги — подменяемые функции игры. Движок даёт порядок, решатель, повторы и отчёт.
2. Решатель сокетов: совместимость краёв (высота, дорога, река, обрыв, проход, запрет), повороты, фиксированные
   клетки, лимиты числа тайлов. Результат детерминирован от зерна и версии генератора.
3. Проверки: достижимость по графу тайлов и связям навигации, допустимые уклоны, расстояния между интересными
   точками, нет изолированных дорог. Правила — данные и хуки игры.
4. Манифест региона: зерно, версия генератора, тайлы с поворотами, POI, связи. Он хранится в сохранении (E8),
   и после обновления игры старый мир не перестраивается.
5. Подземелья: граф комнат из модулей с гарантированным проходом; ручные комнаты — фиксированные узлы графа.
6. Пакетная проверка без окна: `shards worldgen --seeds 1..1000 --report`. Отчёт: сколько зёрен прошло,
   причины отказов, распределение расстояний между точками; падение генератора — с номером зерна.
7. Стриминг: регион загружается целиком за экраном загрузки (по GDD до 10–15 с на SSD). Внутри региона тайлы и
   их LOD подгружаются по расстоянию до игроков. ИИ врагов работает только в активных зонах вокруг игроков.

Граница: набор тайлов, правила биомов и конкретные пороги проверок — игра.

Для ИИ: в `observe` — текущий тайл и ближайшие точки интереса с направлением; инструменты `regen`, `goto_tile`,
`worldgen_report`.

Готово, когда: шаблон генерирует регион 8×8 из тестовых тайлов; 1000 зёрен проходят проверку; одинаковые зерно
и версия дают побайтно одинаковый манифест; переход между регионами с экраном загрузки работает без окна.

## E6. Навигация и ИИ противников

Враги в GDD ходят по заранее запечённой навигации тайлов и глобальному графу (32.4), строятся из шести
поведенческих архетипов, атакуют по жетонам с бюджетом столкновения (20) и выбирают атаки с запретами на опасные
последовательности (21, 22). Речь об игровом ИИ врагов, не об LLM.

Что сделать:

1. Навсетка: запекается для каждого тайла заранее офлайн-командой и сшивается по точкам соединения при сборке
   региона. Глобальный маршрут — по графу тайлов. Запросы пути работают без окна. Кандидаты — vleue_navigator,
   oxidized_navigation, landmass; или своя по графу тайлов.
2. Агенты: следование пути, уклонение от столкновений, ограничение зоны преследования (враг не гонится через
   полрегиона).
3. Каркас поведения NPC: машина состояний или utility-оценка, параметры — в данных, логика — в системах игры.
   Восприятие NPC — видимость через физику и слух как события. Случайность — только через `SimRng`.
4. Режиссёр сражений: жетоны атаки с лимитом от числа игроков (в GDD 2, 3 и 4 — это данные), роли тех, кто ждёт;
   бюджет столкновения и список разрешённых комбинаций.
5. Планировщик атак, общий для врагов и боссов: выбор следующей атаки по весам, дистанции и запретам
   последовательностей (например, нет двух подряд атак, перекрывающих безопасную зону).

Граница: архетипы, поведение конкретных врагов и сценарии боссов — игра.

Для ИИ: состояние NPC, его цель и жетон в describe; смены состояния — в журнал; инструменты `nav_path` и
`npc_state`; оверлей навигации (E11).

Готово, когда: враг в песочнице обходит колонны по навсетке и не выходит за свою зону; при одном игроке из трёх
врагов атакуют не больше двух одновременно; всё совпадает в реплее.

## E7. Сеть и кооператив

GDD: до трёх игроков, хост и два гостя по приглашению, без выделенных серверов (24). Хост авторитетен; клиент
предсказывает своё движение, сразу показывает начало атаки, получает подтверждение урона и плавно исправляет
позицию без rollback (32.5). Мир синхронизируется манифестом. Сначала LAN или прямое подключение, Steam relay
потом. Нужны журнал сетевых событий и симуляция задержки и потерь (32.8). Критерий этапа 3: двое играют без
критических рассинхронов.

Что сделать:

1. Сессия: одиночная, хост, клиент — одна архитектура. Одиночная игра — это хост без гостей.
2. Транспорт: сначала прямое подключение по UDP в LAN. Абстракция транспорта, чтобы добавить Steam relay из E10.
   Плюс транспорт в памяти для тестов: хост и клиенты — отдельные `App` в одном процессе, которые шагают
   синхронно, и сетевые сценарии становятся детерминированными тестами. Кандидаты — lightyear или bevy_replicon.
3. Ввод: клиент шлёт `Intent` с номером тика, хост применяет его на своём тике. Это тот же вход, что пишут
   реплеи, поэтому реплей хоста записывает игру всех игроков.
4. Репликация: компоненты помечаются для репликации; область интереса — вокруг игроков; события (урон, смерть,
   телеграф) идут надёжно; позиции чужих сущностей интерполируются.
5. Предсказание: своё движение и начало своих действий (анимация, эффекты) клиент показывает сразу; урон
   подтверждает хост; расхождение позиции исправляется плавно.
6. Мир через манифест из E5: хост шлёт версию генератора и манифест, клиент собирает регион сам, хэши сверяются.
7. Подключение и отключение: запрос входа с хуком игры «можно ли сейчас» (по GDD — нельзя во время боя с боссом).
   Выход хоста завершает сессию после сохранения.
8. Отладка: журнал сетевых событий, оверлей пинга и потерь, симуляция задержки и потерь пакетов настройкой.

Граница: правила кооп-баланса (масштабирование здоровья, ограничение силы гостя, персональная добыча) — игра.
Движок даёт число игроков, их id и события входа и выхода.

Для ИИ:

- агент привязан к конкретному игроку, `observe` идёт от его лица;
- хост и один-два клиента без окна запускаются одной командой, у каждого свой порт `shards`;
- проверка рассинхрона: хэши реплицируемого состояния у хоста и клиентов каждые N тиков, расхождение — в журнал
  и стоп-условие;
- инструменты `net_sim` (задержка, потери) и `net_status`.

Готово, когда: хост и два клиента без окна проводят 30-минутную скриптовую сессию агентов при задержке 150 мс и
потерях 2% без рассинхрона; подключение и отключение не теряют прогресс; сетевые сценарии на транспорте в памяти
идут в CI.

## E8. Сохранения и настройки

По GDD хост хранит мир, а каждый игрок — своего персонажа (24.2). Награды и открытия сохраняются сразу, позиция
восстанавливается у лагеря, есть три циклические резервные копии (32.6). Повреждённые сохранения — один из
главных рисков (36). Настройки и доступность — раздел 29.

Что сделать:

1. Два вида сохранений: персонаж (у каждого игрока) и мир (у хоста). Слоты.
2. Схема сохранения — явные структуры, а не дамп мира. У файла номер версии и цепочка миграций «версия → версия»;
   миграции проверяются тестами на образцах старых файлов.
3. Запись атомарная (временный файл и переименование), с контрольной суммой. Три циклические резервные копии;
   при повреждении — восстановление из копии с записью в журнал.
4. API «сохранить сейчас» для наград и открытий; автосохранение по событиям игры (лагерь, маяк, босс).
5. Реестр сохраняемого: игра отмечает, какие компоненты и ресурсы входят в сохранение персонажа или мира.
6. Настройки на фреймворке настроек Bevy 0.19: графика, звук, управление (переназначение из E2), доступность
   (тряска, размытие, вспышки, размер текста, поле зрения, удержание или нажатие). Сохраняются между запусками.

Граница: какие поля персонажа и мира сохраняются и как выглядят слоты — игра.

Для ИИ: инструменты `save_game`, `load_game` и `save_check` — сохранить, загрузить и сравнить хэш сохраняемого
состояния. Повреждённый файл даёт понятную ошибку в журнале.

Готово, когда: круговой тест «сохранить → загрузить» на 1000 случайных состояниях не теряет данных;
повреждённый файл восстанавливается из копии; файл старой версии мигрирует и загружается.

## E9. Интерфейс, звук, локализация

GDD требует HUD (здоровье, выносливость, фляга, техники с перезарядкой, Эхо, стойкость цели, компас, союзники,
цель задания), около десяти экранов и сравнение предметов (27). Звук должен помогать читать бой, а музыка —
меняться слоями (31). Текст локализуется, процедурный текст собирается из целых фраз (6.3, 25.2).
Доступность — 29.2.

Что сделать:

1. Набор игровых виджетов на Bevy UI и BSN: полосы (здоровье, выносливость, стойкость), иконки с перезарядкой,
   лента компаса с метками направлений, рамки союзников, подсказки, списки, сетки, вкладки, сравнение
   «было → стало».
2. Стек экранов: открыть, закрыть, назад. В одиночной игре меню ставит мир на паузу, в сетевой — нет (GDD 29.2).
   Навигация геймпадом и фокус.
3. Темы и масштаб текста; подписи доступности (AccessKit) у всех элементов.
4. Локализация: таблицы строк (кандидат — Fluent), смена языка без перезапуска, сборка процедурного текста из
   целых локализованных фраз с параметрами.
5. Звук: шины (общая, музыка, эффекты, интерфейс) с громкостью из настроек; адаптивная музыка со слоями
   «исследование, напряжение, бой» и плавными переходами по состоянию игры; пространственные звуки с приоритетами
   и лимитом голосов; звуковые метки атак из E3.

Граница: сами экраны игры (инвентарь, таланты, кузница), тексты и музыка — игра.

Для ИИ: дерево интерфейса в `observe` (экран, элементы, значения, фокус); инструменты `ui_click`, `ui_navigate`,
`ui_read`; текущий слой музыки в describe.

Готово, когда: в шаблоне есть HUD и два экрана на виджетах движка; агент проходит меню только через дерево
интерфейса; язык переключается на лету; музыка меняет слой при входе в бой.

## E10. Рендер, производительность, платформа

GDD: низкополигональный стиль с вершинными цветами и акцентными эффектами (30); 60 FPS в 1080p на среднем ПК,
растительность инстансами, LOD, пулы, загрузка региона до 10–15 с (32.7); Windows и Steam с лобби и relay
(1, 24, 32.5).

Что сделать:

1. Стилизованные материалы: вершинные цвета, простое освещение, контуры для читаемости, пресеты для low-poly.
2. Растительность и мелкие объекты: рассыпка по тайлам с инстансингом, LOD через диапазоны видимости, отсечение.
3. Эффекты: частицы (кандидат — bevy_hanabi) с пулами; декали зон атак для телеграфов из E3.
4. Бюджеты: время кадра и тика (задача 11), счётчики сущностей и отрисовок в `status`; автотест
   производительности на эталонной сцене в релизной сборке.
5. Steam (кандидат — bevy_steamworks): лобби и приглашения, relay-транспорт для E7, достижения, облачные
   сохранения.
6. Сборка под Windows: релизный профиль, упаковка ассетов, иконка, проверка запуска на чистой машине.
7. Обработчик падений: лог, краш-реплей (из задачи 1) и сведения о системе в один файл для отчёта.
8. Скриншоты без окна: камера рендерит в изображение — для CI и агентов на машинах с GPU.

Граница: модели, материалы, эффекты конкретных атак и арт — игра.

Для ИИ: `perf` в `status` и `step`; инструмент `screenshot`, который работает без окна; счётчики отрисовок.

Готово, когда: эталонная сцена (регион 8×8 с растительностью и 15 врагами) держит 60 FPS в 1080p на целевом ПК;
сборка Windows запускается на чистой машине; два игрока соединяются через Steam relay.

## E11. Инструменты разработчика и слой ИИ

GDD (32.8) требует: просмотр зерна, генерацию сотен регионов, проверку достижимости, переход к фазе босса,
бессмертие и замедление, журнал сети, проверку сохранений, визуализацию хитбоксов, состояние ИИ, симуляцию
задержки. Главная идея движка — всё это доступно агенту через `shards` так же, как человеку.

Что сделать:

1. Внутриигровое меню разработчика и консоль вызывают те же инструменты, что и `shards`, через одну точку входа
   `call_tool`.
2. Оверлеи: хитбоксы, хёртбоксы и зоны атак; навсетка и пути; состояние NPC; сеть (пинг, потери); границы тайлов
   и сокеты.
3. Инструменты: бессмертие, телепорт к тайлу или точке, переход к фазе босса, спавн префаба; замедление уже есть
   (`speed`).
4. Снапшоты: сохранить и загрузить состояние в любой тик (DynamicWorld). Реплей может начинаться со снапшота,
   а переход к фазе босса — грузить снапшот.
5. Восприятие 3D-мира: `clearance` по восьми направлениям (свободно, стена, обрыв, вода — с расстоянием),
   `path_to` с расстоянием и поворотами, видимость лучами физики вместо коробок `AiOccluder`.
6. Связать слой ИИ с модулями: дерево интерфейса (E9), привязка агента к игроку и стенд «хост + клиенты» (E7),
   инструменты сохранений (E8) и генератора (E5).
7. Сценарные тесты: файл сценария (команды `shards`, ожидания и инварианты из задачи 9) запускается в CI без
   окна. У каждого модуля — свой набор эталонных сценариев.

Граница: читы и меню, которые увидит игрок, — игра; всё для разработки — движок.

Готово, когда: каждый пункт списка 32.8 GDD доступен и из меню разработчика, и из `shards`; сценарии всех модулей
идут в CI.

## Порядок по фазам

Фазы идут по этапам GDD. Приёмка фазы складывается из пунктов «Готово, когда» её модулей и проверяется скриптами
в CI. E4, E6, E9 и E11 делаются частями: в каждой фазе только то, что нужно её приёмке.

Рабочая схема фаз (исходная диаграмма в документ не перенесена; восстановлена по тексту ТЗ и этапам GDD):

| фаза | этап GDD | модули |
|---|---|---|
| A | прототип боя (GDD 39) | E1; E2; E3; из E4 — база контента, префабы, `content check`, детерминированная загрузка; из E11 — оверлеи боя, бессмертие, спавн префаба, сценарные тесты |
| B | мир | E5; E6; из E4 — уровни из Blender; из E11 — `clearance`/`path_to` по навсетке, снапшоты |
| C | кооператив (этап 3) | E7; E8; из E11 — стенд «хост + клиенты» |
| D | контент и интерфейс | E9; остаток E4 и E11 |
| E | платформа | E10 |

Сетевую модель закладывайте уже в фазе A, хотя сам E7 — фаза C: движение и действия сразу считаются по тикам и
несут сетевые id, хост авторитетен. GDD прямо предупреждает, что поздно добавленный кооператив заставит
переписать почти все системы.

## Готово, когда

Движок готов для «Осколков Предела», когда на нём собирается отдельная игра без правок движка.

- Шаблон игры в отдельном репозитории зависит только от `shards` и содержит: персонажа с движением из E2, бой на
  данных из E3, врага с навигацией из E6, сгенерированный регион из E5, кооп на двоих из E7, сохранение из E8,
  HUD и меню из E9.
- Всё это управляется через `shards` без окна; сценарии каждого модуля идут в CI.
- В коде движка нет имён контента из GDD.
- README движка объясняет по шагам, как сделать игру на Shards.
